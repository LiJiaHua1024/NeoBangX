# 任务

这是一次 More 请求：老师认为已有的错因还不够，想看看还有没有别的本质错因。你已经通过对话历史看到了题目、诊断过程和目前已有的全部错因，不需要重新复述它们。

# 唯一目标：找到真正独立的新错因，找不到就诚实说没有

这里最容易出问题的地方是：当确实没有新的独立机制时，你可能会倾向于硬凑一条出来——把已有某条错因换个说法、拆出一个更细的子情况，或者把干扰项设计里一个次要的、依附性的细节包装成"新错因"。

不要这样做，原因是：如果这一条新错因和已有某条其实没通过独立性检验（讲透已有那条会自动带掉这条"新"的），下游会为它单独生成一整套讲解和迁移题，最后老师会看到两份几乎重复的内容——这比"直接告诉老师没有更多错因"体验更差，也会让老师之后不再信任 More 这个功能。

所以：**返回空数组是一个完全正常、被期待的正确结果，不是任务失败。** 你不需要为了让这次请求"看起来有产出"而降低判断标准。

# 判断方法

对每一个候选新错因，逐一和已有的全部错因做独立性检验（方法和主分析一致）：

> 如果学生已经彻底掌握了已有某条错因对应的方法论，他会不会自动就不再犯这个"新"错因描述的错误？

只有当这个候选新错因对已有列表中的**每一条**都通不过上面这个检验（也就是真正独立于所有已有错因），才把它作为新错因输出。如果检验后发现所有候选都过不了这一关，就返回空数组。

不要因为"这是 More 请求，应该有产出"而放松这个标准；也不要因为要"保守"就把明明独立的新机制也漏掉不写——同样按独立性检验判断，不要主观决定条数。

# 输出前自检

1. 每一条新错因，是否已经和已有列表里的每一条都做过独立性检验？
2. 如果最终返回了空数组，是因为真的检验不出独立的新机制，而不是因为图省事？
3. 语言风格是否和主分析一致：具体到机制、但不堆砌术语？

# 输出格式

只输出合法 JSON，不要 Markdown 代码围栏、标题或解释。格式必须是：

{"causes":["新错因 1","新错因 2"]}

如果确实没有新的本质错因，返回：

{"causes":[]}
